# 开机菜单管理器设计文档

> 版本：v0.1（讨论稿）  
> 日期：2026-11-16  
> 适用场景：树莓派 3B/4B + SSD1306 OLED + USB 键盘  
> 目标：让小车脱离 SSH 也能完成**配网 → 启动应用 → 退出回菜单**全流程

## 一、需求拆解与核心约束

### 1.1 用户原始需求

| 2 | 顶栏网络状态 | WiFi / 有线 两个图标，显示是否连接 |

| 5 | **二级菜单（2026-11-16 新增）** | 主菜单 6 项，「启动应用」进子菜单，子菜单第一项为「返回上级」 |
| 6 | 应用启动 | 子菜单里选择已有应用快速启动（registry 驱动，可扩展） |
| 7 | 退出回菜单（2026-11-16 分析确认） | 异步 watch 线程 wait_for_exit → killpg 清残留 → reinit OLED → exit_banner 过渡 → 自动回应用子菜单 |

- 树莓派：Bookworm 64-bit，**systemd 启动**（stdin 可能是 /dev/null，不能依赖 termios 读键）

## 二、整体架构

### 2.1 进程模型（核心设计）

```
systemd(1)
└── aitank-menu.service          ← 常驻轻量进程（本设计文档要实现的）
    ├── [线程] OLED 渲染循环      ← 10 FPS，只在菜单状态下写屏
    ├── [线程] 键盘事件监听      ← evdev 读 /dev/input/eventX
    ├── [线程] 网络状态轮询      ← 5 秒一次，读 nmcli / ip 输出
    ├── [空闲] 应用子进程占位    ← 菜单状态下为 None
    │
    └── 用户选择「启动 PetCar」
        └── fork + exec 启动子进程
            ├── 传递 OLED fd     ← 子进程继承菜单的 I2C fd，直接写屏
            ├── subprocess.wait() ← 菜单阻塞等待子进程退出
            └── 子进程退出 → 菜单 killpg 清残留 → 收回 OLED 控制权 → 刷新菜单
```

**关键约束**：同一时刻只有一个进程持有 OLED 写权限。菜单和应用**不会同时写屏**——要么菜单写，要么应用写，通过 fd 所有权切换实现。

### 2.2 OLED 所有权切换机制

**推荐方案：fd 传递**（避免重复 init I2C 的 200ms 延迟）

```python
# 菜单进程 fork 前
import os, fcntl
oled_fd = drv.device.serial._device.fileno()  # luma.oled 底层 I2C fd
os.set_inheritable(oled_fd, True)

# 启动子进程时传递 fd
subprocess.Popen(
    ["python3", "-m", "petcar.main", "--flask"],
    pass_fds=[oled_fd],
    start_new_session=True,  # 子进程进新会话，避免信号串扰
    ...
)

# 子进程（PetCar）启动时检测继承的 fd
# 如果存在 PETCAR_OLED_FD 环境变量，就用这个 fd 初始化 luma.oled
# 否则自己 open I2C（兼容非菜单启动的场景）
```

**退避方案：子进程自己 init OLED**  
如果 fd 传递太复杂，就让子进程启动时重新 open `/dev/i2c-1`，退出时 close。菜单进程在子进程启动后就停止写 OLED，子进程退出后再重新 init。代价是启动延迟 +200ms。

### 2.3 键盘输入方案

**必须用 `evdev` 直接读 `/dev/input/eventX`**——因为 systemd 启动的服务 stdin 是 /dev/null，termios 方案完全不可用。

```bash
# 安装依赖
pip install evdev

# 查找键盘设备
ls /dev/input/by-id/ | grep keyboard
# 例如：usb-USB_Keyboard-event-kbd → /dev/input/event3
```

**键盘事件处理逻辑**：
- 启动时扫描 `/dev/input/event*` 找 EV_KEY 设备
- 监听 EV_KEY 事件，把键码映射成字符/功能键
- 热插拔支持：启动时绑定一次，运行中如果设备消失 → 通知用户重插

**菜单交互规则（128×64 屏幕限制，必须极简）**：
| 按键 | 功能 | 说明 |
|------|------|------|
| `1-9` | 选择菜单项 | 主菜单最多 9 项，数字直接选 |
| `↑↓` | 移动光标 | 子菜单用 |
| `Enter` | 确认 / 启动 | 选应用后按 Enter 启动 |
| `ESC` | 返回上级 / 取消 | 输入密码时取消 |
| `← Backspace` | 退格 | 输入 WiFi 密码时 |
| `?` | 显示帮助 | 底栏临时显示快捷键说明 |

**WiFi 密码输入界面（物理键盘直接打字，无软键盘）**：
```
┌─ 连接 WiFi ──────────────┐  ← 顶部标题
│ SSID: MyHome-5G          │  ← 当前选中的 WiFi
│ PWD: ********_           │  ← 密码输入行（* 隐藏，光标用 _）
│                          │
│ [Enter] 连接  [ESC] 取消 │  ← 底部提示
└──────────────────────────┘
```
- 物理 USB 键盘直接打字输入所有字符（大写/数字/符号/退格全有）
- Backspace 删，Enter 提交，ESC 取消
- 密码在屏幕上显示为 `*`，回显不泄露
- 不支持中文 SSID / 密码（WiFi 规范本身就要求 ASCII）

### 2.4 网络管理方案

**必须用 NetworkManager + nmcli**——树莓派 Lite 版默认没有图形化网络管理，但 nmcli 是最好的命令行接口，支持 WiFi 扫描、密码连接、IP 查询。

#### 2.4.1 系统配置（一次性）

```bash
# 1. 安装 NetworkManager
sudo apt install -y network-manager

# 2. 让 eth0 和 wlan0 由 NM 托管
sudo nmcli device set eth0 managed yes
sudo nmcli device set wlan0 managed yes

# 3. 给 aitank 用户 polkit 权限（无密码调用 nmcli connect）
sudo tee /etc/polkit-1/localauthority/50-local.d/45-aitank-nm.pkla <<'EOF'
[aitank 无密码 nmcli]
Identity=unix-user:pi
Action=org.freedesktop.NetworkManager.*
ResultAny=no
ResultInactive=no
ResultActive=yes
EOF

# 4. 重启 NM 服务
sudo systemctl restart NetworkManager
```

#### 2.4.2 菜单里的网络功能映射

| 菜单功能 | nmcli 命令 | 界面显示 |
|---------|-----------|---------|
| 顶栏 WiFi 状态 | `nmcli device status wifi | grep connected` | 🔲 未连 / 📶 WiFi-5G |
| 顶栏有线状态 | `nmcli device status eth0 | grep connected` | 🔲 未连 / 🌐 已连接 |
| 扫描 WiFi | `nmcli device wifi list` | 列表：信号+SSID+加密方式 |
| 连接 WiFi | `nmcli device wifi connect <SSID> password <PWD>` | 进度条 + 成功/失败提示 |
| 显示 IP | `ip addr show wlan0/eth0` | 底栏显示 `192.168.1.101` |

#### 2.5.2 子进程生命周期管理

```python
# 伪代码：启动应用
def launch_app(app_config):
    p = subprocess.Popen(
        app_config["command"],
        cwd=app_config["cwd"],
        env={**os.environ, **app_config.get("env", {})},
        start_new_session=True,          # 进新会话组
        pass_fds=[oled_fd] if app_config.get("needs_oled") else [],
        stdout=subprocess.PIPE,          # 可选：日志重定向
        stderr=subprocess.PIPE,
    )
    return p

# 伪代码：等待退出 → 清理 → 回菜单
p = launch_app(selected_app)
exit_code = p.wait()                     # 阻塞等待

# 1. 清理残留子进程（比如 PetCar fork 的 piper）
os.killpg(p.pid, signal.SIGTERM)         # 杀整个会话组
try:
    os.waitpg(p.pid, os.WNOHANG)         # 非阻塞收尸
except ChildProcessError:
    pass

# 2. 收回 OLED 控制权
drv = reinit_oled_driver()               # 或重置继承的 fd

# 3. 刷新菜单
render_main_menu()
show_exit_banner(f"{app_name} 已退出 (code={exit_code})", duration=2)
```

#### 2.5.3 退出场景覆盖

| 退出场景 | 处理 |
|---------|------|
| 应用正常退出（exit 0） | 显示退出码 → 回菜单 |
| 应用崩溃（exit ≠ 0） | 显示错误码 + 应用最后 20 行日志 → 回菜单 |
| 应用被 kill（SIGKILL） | killpg 清残留 → 回菜单 |
| 用户在菜单触发杀进程（新需求：长按 Esc 2 秒杀当前应用） | killpg → 回菜单 |
| 树莓派断电 | systemd 重启服务 → 重新进菜单 |

## 四、systemd 开机自启配置

**文件**：`/etc/systemd/system/aitank-menu.service`

```ini
[Unit]
Description=AITank 开机菜单管理器
After=network-online.target NetworkManager.service
Wants=NetworkManager.service

[Service]
Type=simple
User=pi
WorkingDirectory=/home/pi/AITank
Environment=PYTHONUNBUFFERED=1
Environment=PATH=/usr/local/bin:/usr/bin:/bin
ExecStart=/usr/bin/python3 -m aitank_menu.main
Restart=always
RestartSec=3
# 让服务可以访问 /dev/input 和 I2C
SupplementaryGroups=i2c,input

[Install]
WantedBy=multi-user.target
```

**安装步骤**：
```bash
sudo cp aitank-menu.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable aitank-menu    # 开机自启
sudo systemctl start aitank-menu     # 立即启动
sudo systemctl status aitank-menu    # 查看状态
```

## 六、待确认决策（需要你拍板）

### 【待确认 1】OLED fd 传递 vs 子进程自己 init
- **方案 A（推荐）**：菜单 fork 时用 `pass_fds=[oled_fd]`，子进程从环境变量读 fd 号 → 启动快 + 无竞争
- **方案 B（退避）**：菜单启动子进程后停写 OLED，子进程自己 open I2C → 简单但 +200ms 延迟
- 你倾向哪个？（我建议先做 B 跑通 MVP，再升级到 A）

### 【待确认 2】WiFi 连接的权限处理
- **方案 A**：polkit 配置免密码 nmcli → 键盘输完密码就能连，体验好
- **方案 B**：菜单里输入 sudo 密码 → 每次连 WiFi 都要输 root 密码，麻烦但安全
- 你倾向哪个？（我建议 A，polkit 一次性配置后就免了）

### 【待确认 3】应用运行中能否触发菜单快捷键
- 是否需要**隐藏快捷键**（比如 `Ctrl+Shift+X`）强制杀当前应用回菜单？
- 还是应用自己退出，菜单不干预？
- 我建议**加快捷键**——万一应用卡死（比如 PetCar 加载 whisper 崩了），总不能拔电

### 【待确认 4】顶栏刷新频率
- 网络状态 5 秒轮询一次足够？
- 时间 1 分钟刷新一次足够？
- 还是要更快？（快了费 CPU，慢了用户感觉不实时）

### 【待确认 5】第一版要支持哪些菜单项
- MVP 阶段先做：主菜单（选应用）、WiFi 设置（扫描+连接）、网络状态（显示 IP）、重启/关机？
- 还是要更多（比如亮度调节、声音测试、系统信息）？
- 我建议 MVP 就 4 项，先跑通核心流程

|------|------|------|
| Bookworm Lite 默认没装 NetworkManager | nmcli 不可用，配网功能失效 | 安装步骤写进 README，启动时检测 nmcli 是否存在，不存在则在顶栏显示「需安装 NetworkManager」 |
| evdev 找不到键盘（设备名变了） | 菜单无法操作 | 启动时扫描 `/dev/input/by-id/*keyboard*`，找不到则打印到日志，顶栏显示「未检测到键盘」 |
| 应用崩溃后残留子进程（piper/ffmpeg） | 下次启动应用端口/设备被占 | `os.killpg` 杀整个会话组 + 子进程退出时给 3 秒宽限期，超时 SIGKILL |
| OLED fd 被菜单和应用同时写 | 屏幕花屏 | 严格实现所有权切换：菜单启动应用后立刻停止写 OLED 线程，应用退出后再恢复 |
| 系统重启后 WiFi 密码丢失 | 用户下次还要重新连 | nmcli 连接成功后自动保存 profile（默认行为），下次开机自动连 |

## 九、与现有 PetCar 的兼容性

### 9.1 不改动 PetCar 代码的场景
- 菜单作为独立进程，PetCar 完全感知不到菜单的存在
- `python3 -m petcar.main` 直接运行 → 自己 init OLED，不依赖菜单
- 菜单启动 PetCar → 如果不实现 fd 传递（方案 B），PetCar 也是自己 init OLED

### 9.2 需要改 PetCar 的场景（如果选方案 A）
- PetCar `_connect_all()` 里 `create_oled_driver()` 需要检测环境变量 `PETCAR_OLED_FD`
- 如果存在，就用 `os.fdopen(int(fd_env))` 初始化 luma.oled，跳过 `device = ssd1306(i2c(...))` 的 open 步骤
- 改动量：约 10 行，只在 `petcar/drivers/oled.py` 里加一个分支

### 9.3 其他兼容性
- PetCar 的 `finally` 清理逻辑（电机/摄像头/OLED/piper）**完全不变**——菜单只是父进程，不干预子进程内部的清理
- Ollama 开机自启**不变**——菜单不碰 systemd 的 ollama 服务
- start.sh **不动**——如果用户想跳过菜单直接启动 PetCar，还是可以用 `./petcar/start.sh`
